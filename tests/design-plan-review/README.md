# design-plan-review 受控行为测试

使用真实子 Agent 运行 [当前 skill](../../skills/design-plan-review/SKILL.md)，验证扫描对齐、对抗补漏、修订回查和资料缺失时的处理。夹具故意保留问题；复跑时只修改临时副本，不修正这里的原始输入。

## 复跑方式

1. 将要测试的 `fixtures/` 子目录复制到临时目录。
2. 给主 Agent 当前 skill 的位置、临时案例的全部输入文件，以及允许修订的范围。
3. 按当前 skill 主动创建两个通用子 Agent，省略自定义角色参数，将技能附带的 A、B 完整 `developer_instructions` 分别传入；不注册、不依赖原生角色。先独立审查，再完成 B 质疑、A 回应、B 复核。使用不复制父线程历史的派生方式，显式传入本轮材料。
4. 每次修订后按 skill 完整重扫、重新调用双方对抗。保存问题清单、实际 Agent 标识、各阶段文件指纹及往返结果。
5. 完成后再用下面的预期核对。不要提前把本 README 的答案、怀疑点或修复建议交给被测 Agent。

## 案例一：领券方案的冲突与遗漏

输入为 [coupon-claim](fixtures/coupon-claim/) 下的四份文件：

- `requirements.md`：固定业务目标。
- `service-contract.md`：固定接口、数据与部署环境。
- `design.md`：允许修订的方案。
- `plan.md`：允许修订的落地计划。

预期反例：

| 编号 | 类型 | 稳定触发路径 |
| --- | --- | --- |
| S-001 | 已写约定冲突 | 需求、上游和方案上限均为 100，计划却初始化为 200；第 101 个用户仍可能领到券。 |
| O-001 | 设计遗漏 | 插券持久化后，扣额度失败；未规定共同事务，留下券已发但额度未扣的部分结果。 |
| O-002 | 设计遗漏 | 已有 99 张券、剩余 1 张，两个实例上的不同用户均先查到有额度，再各自发券，导致超发。 |
| O-003 | 设计遗漏 | 同用户两个首次请求均查无券，再生成不同券号；仅券号主键无法阻止同一用户领两张。 |

验收重点：

- 扫描能发现 S-001，并修正计划，不能通过修改固定需求或上游来消除冲突。
- A、B 对抗能提出必要处理缺口，并完成真实回应和复核；不得只凭口头修复思路销项。
- 遗漏写入方案与计划后，必须先完整重扫四份，再开始新一轮双方完整对抗。
- 只有旧问题已复核、最后扫描无冲突、随后对抗无新有效遗漏，才能报告本次范围通过。

## 案例二：缺少关键上游契约

输入为 [missing-provider](fixtures/missing-provider/) 下的 `requirements.md`、`design.md`、`plan.md`，以及它们引用的 `provider-contract.md`。最后这个文件故意不存在，不要创建占位文件。

本例只读，不允许修改、新增资料，也没有实际上游服务可查询。

预期结果是保留关键材料缺口，明确尚不能核验资源占用成功、拒绝、超时、重试和幂等语义。可以检查不受影响的部分，但不能据此宣布整个审查通过，也不能把“缺少证据”直接判成“已证实误报成功”。

## 2026-10-22 实测结果

以下记录对应当时的原生角色调用方式；不能据此宣称已验证后续改为主动传入角色指令的调用方式。

环境为 Codex CLI 0.163.0。使用仓库现有两个原生角色，未覆盖模型或推理设置；每个角色只审查，协调器统一修订临时业务材料。

| 检查项 | 观测结果 |
| --- | --- |
| 扫描发现冲突 | S-001 命中，计划初值 200 改为 100；固定需求及服务约定未改。 |
| 对抗发现遗漏 | O-001～O-003 全部命中，双方实际完成质疑、回应、复核。 |
| 统一补充 | 临时方案和计划补入同事务、数据库行锁、组合唯一约束、重试规则及相应验收路径。 |
| 返回扫描与复审 | 共 3 遍完整扫描、2 轮完整对抗；第二轮复用同一 A、B，以新任务唤醒并完整重读。 |
| 版本证据 | 10 组共 40 份快照独立核对通过；最终扫描与第二轮对抗材料一致。 |
| 无问题后结束 | 第二轮未发现新必要遗漏，已确认问题全部完成文档修订及复核后才结束。 |
| 关键资料缺失 | 1 遍现有材料扫描、1 轮有限对抗后保留“待确认，不能通过”，未编造或新增上游契约。 |

领券案例真实角色标识：A 为 `/root/review_a`，B 为 `/root/review_b`；原生角色选择分别为 `design_plan_proponent`、`design_plan_challenger`。首次使用 `fork_turns="none"`，回应和第二轮复审使用 `followup_task` 复用、唤醒。

两个案例均达到各自的预期行为；“资料缺失案例正确不通过”是该负向测试的成功结果。本次验证真实执行了 Agent 工作流，未实现领券或预约业务代码，也未实际运行数据库、并发、故障注入或部署验收。上述反例是基于文档和给定环境的交错推演。

## 2026-10-24 主动调用验证

验证新调用方式：直接使用当前会话的 `spawn_agent`，省略 `agent_type`、模型及推理参数，以 `fork_turns="none"` 分别创建 `/root/active_review_a`、`/root/active_review_b`。消息完整传入技能 TOML 的 `developer_instructions`，以及 `missing-provider` 三份文件正文、契约读取失败事实和本轮范围；没有向任何目录复制配置。

实际完成双方独立审查 → 将 B-01 质疑交给 A → A 回应 → 将 A 的回应交给 B → B 复核。后续回合使用 `followup_task`，取得双方实际返回结果。

- A、B 均保留必要契约缺失的问题，本轮不能通过；没有编造接口或成功语义。
- A 首轮还将“拒绝路径未明确”判为遗漏；交换时主审要求核对“按契约成功及失败语义更新状态”这段已有文字。A 撤回证据不足的判断，B 实际复核认可应改为无法判断，避免把材料缺失认定为已证实设计错误。
- 新方式的真实派生与往返已验证。此轮未修改业务夹具，未复跑领券案例的完整修订循环，也未验证不同机器上的安装发现；旧的完整循环结果仍仅见上节历史记录。

测试时项目已有旧的原生配置，但本轮派生没有选择自定义角色，指令直接传入通用子 Agent；不将本次调用成功冒称为原生配置加载成功。Skill 格式、角色 TOML 和本地说明链接检查通过。
