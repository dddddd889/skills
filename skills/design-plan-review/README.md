# 通用对抗审查

对用户指定的已有对象进行审查，分两步循环执行。方案、实施计划、代码只是应用示例，审查范围不限定为这些类型。

- **反复扫描对齐**：比较当前内容、上下文和上下游，发现冲突、矛盾、未同步的修改。
- **Agent 对抗补漏**：A 推演被审对象如何满足目标并回应质疑，B 用具体反例挑战前提、寻找遗漏或缺陷。

主 Agent 组织审查、汇总问题，并在授权范围内统一修订或修复，不从零开发。只要求审查时不修改文件。具体执行规则见 [SKILL.md](SKILL.md)。保留调用名 `design-plan-review`，兼容已有安装。

检查项随对象和目标调整，例如：

| 对象示例 | 检查示例 |
| --- | --- |
| 方案 | 取消订单与支付同时发生时，状态如何处理？ |
| 实施计划 | 方案要求幂等，是否有任务实现并验收？ |
| 代码 | 两个请求是否都能通过检查，实际导致重复处理？ |

## 显式调用

本技能关闭自动匹配触发。需要审查时，由你手动选择技能或输入：

```text
$design-plan-review
审查对象与范围：……
目标依据、上下文与上下游：……
本次仅审查 / 审查并修复：……
```

不用先把对象归入固定类型，也不要求提供上述三类文件。普通讨论不会自动启用本技能；显式调用后，主 Agent 按下面的流程组织 A、B。

## 一次提问，多轮完整审查

每个 A 代表主 Agent 交付的一轮完整状态，后续轮次基于上一份状态及真实材料重新找问题，无需反复输入“继续”：

```text
Q：启动审查
A1：完整扫描、A/B 对抗、授权修订与验证，交付完整状态 S1
A2：新的一对 A/B 独立审查 S1 对应材料，再核对 S1，交付完整状态 S2
A3：新的一对 A/B 独立审查 S2 对应材料，再核对 S2，交付完整状态 S3
……最终通过，或停止并交付完整当前状态
```

完整状态包含：原始目标与授权范围、审查输入与交付版本及上下游材料、全部问题与证据及处理状态、修订和实际验证、未覆盖与待确认项、本轮结论与下一步。长材料引用可读取的固定版本或只读快照，不能只写变化摘要或依赖上一条对话。

主 Agent 每轮新建一对不继承旧对话的 A/B；先给原始目标与最新真实材料独立找问题，再补发上一轮完整状态核对，避免先入为主。同轮可以往返，跨轮不复用。默认最多 3 轮，通常第 2 轮独立验收通过就结束，不凑轮数；修订后的版本保持“待独立复审”。主 Agent 的轮内进度消息不能代替完整状态，必要确认、轮数上限、用户明确指定的其他上限和停止规则继续有效。

## 流程图

```mermaid
graph TD;
    input["确定目标、范围和材料版本，轮数默认最多 3 轮，记录用户其他上限（如有）"];
    scan["主 Agent 扫描本次范围、上下文和上下游"];
    conflict{"存在冲突、矛盾或约定未对齐？"};
    align["主 Agent 按授权修正不一致，执行适用验证"];
    record["记录未解决冲突，继续可完成的对抗检查"];
    call["每轮新建无旧对话历史的 A/B，先只给目标与最新原始材料"];
    debate["先独立找问题，再核对上一完整状态并对抗，主 Agent 验证"];
    omission{"仍有必要问题、影响结论的待确认项或必要验证未完成？"};
    patch["主 Agent 验证反例，按授权修订被审对象及关联内容"];
    state["交付本轮完整状态，修订版本待独立复审"];
    acceptance{"已基于上一完整状态完成新一轮验收，且本轮无实质修订？"};
    pending["停止：轮数用尽、达到用户其他上限、无进展或无法闭环，交付完整状态，不报告通过"];
    finish["通过：必要问题已复核、扫描无冲突、对抗无新问题、必要验证通过"];

    input --> scan;
    scan --> conflict;
    conflict -->|"有，且可修正"| align;
    conflict -->|"暂不能修正"| record;
    record --> call;
    align -->|"再次完整扫描"| scan;
    conflict -->|"没有"| call;
    call --> debate;
    debate --> omission;
    omission -->|"有，且可修复"| patch;
    omission -->|"暂不能闭环"| pending;
    patch -->|"重新扫描与适用验证后"| state;
    state -->|"未触发停止规则，进入新一轮"| scan;
    state -->|"轮数用尽，仍待复审"| pending;
    omission -->|"没有"| acceptance;
    acceptance -->|"否，先交付状态再独立验收"| state;
    acceptance -->|"是"| finish;
```

每次修改后，都先重新完整扫描本次范围及受影响上下游，交付完整状态，再由下一轮新 A/B 独立复审，不能只让发现问题的一方验收。只审查而不修复时，也交付完整状态并保留未解决项。

每轮完整状态交付后，在授权内且未触发停止规则时继续下一轮；轮内可报告实际进展。最后通过或停止时，仍给出独立完整的当前状态。

流程中所有步骤及内部循环都受以下规则限制，触发时转入“停止”，不强行完成下一轮：

- **防死循环**：默认整次审查最多 3 轮（首轮计入），你另指定轮数时优先采用你的设置。最后一轮完成并交付完整状态后，仍有问题或待独立复审就报告未完成，不自动加一轮；换 Agent、修订或重新扫描不重置轮数。时间和调用次数仅在你明确指定时才设限，有总时限时全流程共用、重试不重置，未指定则不要求确认延长。同一问题连续两次复查或往返没有有效进展就停；已闭环问题只凭新证据或相关修改重开。
- **防过度设计与范围扩大**：必要问题才阻断，可选优化单列，A/B 可以没有新增问题。授权内的必要依赖（包括间接依赖）可以继续处理，只处理足以正确完成原目标的部分，不接管其他问题，也不要求逐步论证。明显扩大范围、改变目标或涉及关键取舍时，主 Agent 汇总依赖关系、必要性与最小方案，先请你确认；确认前暂停扩展部分，继续不受影响的审查。必要依赖未解决，原目标就仍受阻，不能声称完成。

审查通过前必须同时满足：已确认的必要问题全部解决并复核；最新版本完整扫描无冲突；后一轮新建 A/B 先独立检查、再核对上一完整状态并对抗，无新必要问题且无实质修订；适用的必要验证已完成。验证方式随对象选择，例如规则核对、场景推演、结果复算或代码测试，只写验收步骤不算实际执行。缺少关键依据、验证或真实 Agent 回执时，不能无条件通过。轮数用尽、达到用户其他上限或讨论停滞时交付完整状态，停止不等于通过；单个争议停滞不影响其他未触发停止规则的独立检查。

## A、B 的配置

- A：[`design_plan_proponent`](agents/design-plan-proponent.toml)，推演被审对象如何满足目标，用证据回应质疑。
- B：[`design_plan_challenger`](agents/design-plan-challenger.toml)，挑战前提与实际行为，用反例寻找遗漏和缺陷。

这两个 TOML 文件是原生 Codex Agent 定义。`agents/openai.yaml` 是技能展示配置。项目安装和实际调用方式见 [SKILL.md 的子 Agent 说明](SKILL.md#codex-子-agent-定义与调用)。
