# 方案与计划审查

输入是已有的方案、落地计划、相关上下文和上下游文档。主 Agent 不负责从零写方案和计划，只组织审查、汇总问题和统一修订。

保留两道检查，不把流程扩成完整的项目管理制度：

- **扫描对齐**：反复比较已经写出的内容，找冲突、矛盾、约定不一致。
- **对抗补漏**：让两个 Agent 相互质疑，找尚未写出的必要场景、规则和落地步骤。

扫描没有发现冲突，不代表设计没有遗漏；必须继续做对抗审查。

## 分工

| 角色 | 职责 |
| --- | --- |
| 主 Agent | 扫描对齐，调用 A、B，汇总判断问题，统一修订，控制循环 |
| Agent A | 根据需求和现有设计推演完整业务流程，说明如何闭环，并回应 B 的质疑 |
| Agent B | 挑战 A 的推演和设计前提，用具体反例寻找遗漏，持续追问没有解释清楚的部分 |

A 可以承认并补充自己发现的遗漏，不为维护原方案强行辩护。两者不能只分别输出意见；主 Agent 必须交换它们的结论，组织回应与追问。

## 主动创建并调用 A、B

进入本技能后，主 Agent 按流程主动调用子 Agent，不要求用户额外说“开两个 Agent”或先安装角色配置。角色指令随技能提供：

- A：[`agents/design-plan-proponent.toml`](agents/design-plan-proponent.toml) 的 `developer_instructions`，负责推演和回应。
- B：[`agents/design-plan-challenger.toml`](agents/design-plan-challenger.toml) 的 `developer_instructions`，负责反例和追问。

从当前加载的 `SKILL.md` 所在目录解析这些相对路径，不能写死仓库或个人安装路径。使用子 Agent 工具主动派生两个真实的通用子 Agent，并把对应角色的完整 `developer_instructions` 和本轮任务一起作为消息传入；不要只发送 TOML 路径、角色名或一句职责摘要。

首次派生按下面的参数含义调用，使用当前环境工具的等价字段：

- 创建两个独立任务，如 `design_plan_review_a` 和 `design_plan_review_b`。
- 省略自定义角色选择参数，不依赖 `design_plan_proponent` 或 `design_plan_challenger` 已被注册。
- 使用不复制父历史的方式（如 `fork_turns="none"`），显式传入相同的材料位置或正文、上下文、版本、允许操作范围及已有问题清单。两者独立检查前不提供对方的结论。
- 不指定模型和推理强度，沿用主 Agent 设置；子 Agent 只读且不再派生下级。

这是通过完整角色指令主动调用真实子 Agent，不声称已经加载原生自定义角色。`agents/openai.yaml` 只提供技能展示信息；使用本技能不需要向 `.codex/agents/` 或全局配置复制文件，不执行注册或安装命令。仓库保留的原生角色副本仅供旧用法兼容，不能作为当前调用的前提。

保存两个子 Agent 的实际 ID，等待双方首轮结果后交换结论，让 A 回应 B 的质疑，再将 A 的回应交给 B 复核。已结束的 Agent 使用能唤醒新回合的接口（如 `followup_task`），不能仅用只排队的消息接口就声称完成。修订后的复审主动向两个 ID 发起新任务；Agent 已不可用时，用同样的完整指令重新派生并记录新 ID。

调用失败时保留错误和失败阶段，只有实际收到子 Agent 的结果才能记为完成。若父历史不可用（如 `no rollout found for thread id`），确认使用不复制历史并显式传材料的方式重试；仍失败则报告受阻，不让主 Agent 分饰两角替代真实调用。

## 执行流程

### 1. 准备同一份材料

找到用户指定的方案、计划、原始需求、相关上下文和直接关联的上下游文档，明确本次材料版本和允许修订的范围。

缺少关键材料时，先完成不受影响的检查，再向用户说明具体缺口；不能把没有读取到的内容视为已通过。只在授权范围内修订，不因发现冲突就自动改写上下游约定或业务要求。

维护一份简短问题清单即可：`编号｜冲突或遗漏｜依据与触发场景｜处理结果｜是否已复核`。同一个问题沿用编号，不能通过换名字或隐藏旧问题获得通过。

### 2. 主 Agent 反复扫描对齐

每遍完整比较当前文档内部、已有上下文以及上下游之间的约定，重点检查：

- 同一术语、字段、状态、职责的含义是否一致。
- 输入输出、触发条件、先后顺序、成功与失败的含义是否一致。
- 方案承诺的处理方式与落地计划是否冲突。
- 本次修订是否造成其他段落或关联文档未同步。

发现有效冲突就统一修订，然后再完整扫描一遍，不能只检查刚改的段落。直到最新版本的一遍完整扫描没有发现有效冲突，才进入对抗补漏。

### 3. 每轮调用 A、B 做对抗补漏

每次进入此阶段，都实际调用两个审查 Agent，向它们提供同一份最新材料及已有问题清单。可以复用原 Agent，但必须让其重新读取最新版本、完整检查，不能只核对上轮问题。

先让 A、B 独立形成判断，再交换结果进行对抗：

1. A 推演需求如何从开始走到业务结果，解释方案和计划如何支撑这个过程。
2. B 根据材料提出具体反例，指出设计没有处理的必要场景、隐藏前提或缺失步骤。
3. A 逐条回应：引用已有处理方式，或承认遗漏；不能用“实现时再处理”作为已有覆盖的证据。
4. B 检查回应，继续追问未闭环部分。主 Agent 转发必要反馈，直到问题成立、被证据排除，或明确缺少什么信息。

根据业务挑选反例，例如边界条件、失败与部分成功、重复与重试、并发与乱序、权限、历史数据和上线过渡；不机械扩展所有无关场景。

角色长期指令以两个 TOML 定义为准；每轮任务只补充材料版本、文件位置、当前阶段、已有问题及需要回应的对方结论。

如果当前环境不能调用多个 Agent，说明对抗阶段无法执行；单个 Agent 分饰两角不能标记为已完成多 Agent 对抗。

### 4. 主 Agent 补充后回到扫描

主 Agent 按材料和具体反例判断哪些遗漏成立，不按票数或“双方同意”直接判定。需要补充的问题至少说明：什么条件触发、文档哪里缺失、会造成什么后果。

有有效遗漏时，统一补充方案和相应落地计划，更新问题清单；随后必须回到步骤 2。补充可能引入新矛盾，不能直接结束，也不能只让提出问题的 Agent 验收。

重新扫描对齐后，再次调用 A、B，以最新版本展开新一轮完整对抗。

## 结束条件

只有同时满足以下条件，才能报告审查通过：

1. 所有已确认的冲突与遗漏已解决并复核。
2. 最后一次修订后，完整扫描当前文档、上下文及上下游，没有发现有效冲突。
3. 随后基于同一最新版本调用 A、B，完成推演、质疑与回应，没有发现新的有效遗漏。

如果最后一轮又修改了实质内容，上面的扫描和对抗结论就需要重新取得。扫描遍数和对抗轮数是记录，不是通过依据。

遇到关键材料缺失、业务取舍无法自行决定，或争议缺少证据且重复讨论没有进展时，保留具体问题并请求必要信息，标记为“待确认”，不能记为无问题。用户指定轮数或预算且已经用尽时，报告未完成的检查和未解决问题，不假报通过。

结束时简短交付：结论、检查范围、扫描及对抗轮数、修订内容、剩余待确认项。结论表述为“本次范围内未发现未解决的冲突或新遗漏”，不承诺绝对零遗漏。
