# 通用对抗审查

仅在用户显式调用 `$design-plan-review` 或明确点名使用本技能时执行；不要因普通请求提到方案、实施计划、代码或评审就自行启用。触发策略由 `agents/openai.yaml` 的 `policy.allow_implicit_invocation: false` 配置。保留原调用名以兼容已有安装。

输入是用户指定的已有审查对象，以及目标依据、相关上下文和上下游约定。审查对象不限定类型，可以是一份材料、一个实现或多个相互关联的对象。主 Agent 负责组织审查、汇总问题，并在用户授权范围内统一修订或修复，不承担从零编写被审内容；仅要求审查时，输出问题和建议，不改文件。

## 按对象调整检查项

审查方法通用，具体检查项从本次对象的目标、约束、依赖和可验证结果推导，不使用固定的对象类型清单限定范围。下面仅举例说明：

| 对象 | 扫描对齐检查什么 | 对抗检查什么 |
| --- | --- | --- |
| 方案 | 与需求、上下文和上下游约定是否矛盾 | 必要场景、设计前提、失败处理是否遗漏 |
| 实施计划 | 是否落实方案承诺，任务顺序与依赖是否一致 | 必要任务、交付步骤和验收路径是否遗漏 |
| 代码 | 实际入口、调用链、数据和返回行为是否符合需求、方案及接口约定 | 未覆盖的分支、边界、并发、异常、重试及实现缺陷 |

只检查用户指定的对象及相关依赖，不要求补齐示例中的其他类型。只有缺失的信息影响某项判断时，才将该判断标为待确认。多个对象同时提供时，交叉检查它们之间的承诺、依赖和结果是否一致。例如，只审代码时，可用明确的预期行为、接口或现有测试作为依据；缺少方案或计划本身不算缺陷。

保留两道检查，不把流程扩成完整的项目管理制度：

- **扫描对齐**：反复比较对象内部、相关上下文及上下游的规则和行为，找冲突、矛盾、不一致。
- **对抗补漏**：让两个 Agent 相互质疑，用反例挑战前提，找尚未考虑的必要场景、环节或缺陷。

扫描没有发现冲突，不代表没有遗漏或缺陷；必须继续做对抗审查。

## 分工

| 角色 | 职责 |
| --- | --- |
| 主 Agent | 扫描对齐，调用 A、B，汇总判断问题，按授权统一修订或修复、运行验证，控制循环 |
| Agent A | 推演被审对象如何满足目标，用位置和证据回应 B |
| Agent B | 挑战 A 的推演和隐藏前提，用具体反例寻找遗漏或缺陷，追问未闭环部分 |

A 可以承认自己发现的问题，不为维护被审内容强行辩护。两者不能只分别输出意见；主 Agent 必须交换它们的结论，组织回应与追问。

## 每轮完整交付，下一轮独立复审

用户调用一次后，每轮完成扫描对齐、A/B 独立审查与对抗、授权内修订和适用验证，再向用户交付一份完整状态。下一轮基于这份状态及实际材料重新审查；阶段进度不能代替整轮交付。

- **完整状态**：每轮包含原始目标与授权范围；本轮审查输入版本、交付版本及上下文和上下游材料；全部问题的编号、证据和当前处理状态；本轮修订、实际验证、未覆盖与待确认项；本轮结论及下一步。长材料可引用可读取的固定版本或只读快照，不能仅给变化摘要、可变路径或依赖隐藏历史。
- **新审查上下文**：每轮新建一对 A/B，不继承上一轮的对话历史。同轮内可以继续往返，跨轮不复用。先只提供原始目标、约束及最新真实材料，让双方独立形成发现；随后再提供上一轮完整状态，核对旧问题与证据并展开对抗。旧结论是待核验记录，发现新证据时允许推翻，不能只检查旧问题是否销项。
- **独立验收**：首轮形成完整状态后，由下一轮全新的 A/B 复审。只有这轮完整检查没有发现新的必要问题、没有实质修订且必要验证完成，才可最终通过；有修订则交付新状态，预算内进入下一轮。来不及完成独立验收时报告未完成，不靠增加回复条数冒充独立审查。
- **连续执行**：每轮完整状态用 `commentary` 交付后，在预算和授权内继续，无需用户反复输入“继续”；轮内按需报告真实进展。最终通过、触发停止规则，或必须等待用户输入且已无可继续工作时，才用 `final` 独立交付结论及完整当前状态。主 Agent 负责协调，独立审查由本轮新建的 A/B 实际执行。

## 停止与范围控制

- **统一上限**：本次审查总时限默认 20 分钟，可按用户指定调整；另有轮数或调用次数上限时，任一先到即停。扫描、修订、验证、A/B 往返与等待都共用总时限，重试或更换 Agent 不重置。每步开始前检查剩余时间，等待子 Agent 也受剩余时间限制；到限后结束当前等待，不再发起新任务，交付未完成项。
- **无进展就停**：同一问题连续两次复查或往返没有新增有效证据、关闭问题或实质修订，就停止重复讨论，记录争议与需要补充的信息。已排除或已修复的问题，仅在出现新证据或相关内容变化时重开，沿用原编号；新审查从未改动的材料中指出旧关闭理由错误，也属于新证据。
- **必要问题才阻断**：问题必须说明本次范围内成立的场景、依据及对当前目标的影响。区分必要问题、待确认项和可选优化；只有影响当前必要结论的待确认项才阻止通过，可选优化单独列出。A、B 可以报告没有新增问题，主 Agent 可以凭依据驳回质疑。
- **必要依赖与范围确认**：在授权范围内继续处理有具体依据的必要依赖，包括间接依赖；只处理足以正确完成原目标的部分，不接管依赖对象的其他问题，不要求每一步单独论证。优先最小修复，不为回应假设补整套无关设计、文档、机制或测试。依赖链明显扩大任务范围、改变原目标或涉及关键取舍时，由主 Agent 汇总依赖关系、必要性与最小方案，先请用户确认；确认前暂停扩展部分，继续不受影响的审查。必要依赖无法解决时，明确原目标仍受阻，不绕过要求或声称完成。

## Codex 子 Agent 定义与调用

本技能附带两个原生 Codex 自定义 Agent 定义：

- A：[`agents/design-plan-proponent.toml`](agents/design-plan-proponent.toml)，调用名 `design_plan_proponent`。
- B：[`agents/design-plan-challenger.toml`](agents/design-plan-challenger.toml)，调用名 `design_plan_challenger`。

`agents/openai.yaml` 只定义技能展示信息，不注册子 Agent。Codex 从项目 `.codex/agents/` 或个人 `~/.codex/agents/` 读取上述 TOML 格式；仅安装技能目录不会自动注册它们。本仓库的 `.codex/agents/` 已安装这两个定义的普通文件副本；更新角色指令时同步这两个位置。

首次在其他项目使用时，将上述两个 TOML 文件安装到目标项目的 `.codex/agents/`，不覆盖已有不同定义、不自动写入个人全局配置；新建会话确认能够调用这两个名称。原生配置格式依据：[OpenAI 官方子 Agent 文档](https://learn.chatgpt.com/docs/agent-configuration/subagents#custom-agents)。

执行对抗阶段时，优先按这两个调用名派生真实子 Agent。如果当前工具只支持通用子 Agent，则读取对应 TOML 的 `developer_instructions`，将完整指令和本轮材料一起传给两个真实子 Agent；这属于显式指令调用，不能声称已经加载原生配置。两种方式都继承主 Agent 的模型和推理设置。

主 Agent 按轮次记录 A、B 的实际 ID。派生时选择不复制历史的方式（当前工具为 `fork_turns="none"`），显式传入角色指令及本轮材料；没有上下文隔离能力时如实说明，不能宣称独立复审。同轮等待各自独立结果后，补发上一轮完整状态，并将 B 的质疑发送给 A、A 的回应发送给 B；需要时继续往返。下一轮重新派生，不能复用上一轮的 ID。不要把只会排队、不会唤醒已结束 Agent 的消息发送当作已完成任务。

## 执行流程

### 1. 固定对象、依据和版本

找到用户指定的对象、预期行为、相关上下文及直接关联的上下游。明确本次只审查还是审查并修复，以及文件范围和版本；代码审查同时记录分支、基准提交或差异范围（若适用），保留用户已有改动。

两位 Agent 必须审查同一版本；被审对象或相关依据在审查期间发生变化时，旧结论需要复核。缺少关键依据时先完成不受影响的检查，不能把没有读取或执行的内容视为通过。不为使对象通过审查而擅自改写目标依据；例如，不能因为代码不符合要求就反过来改写业务要求、接口约定或测试预期。

维护一份简短问题清单即可：`编号｜冲突、遗漏或缺陷｜依据与触发路径｜处理结果｜验证与复核`。同一个问题沿用编号，不能通过换名字或隐藏旧问题获得通过。

### 2. 主 Agent 反复扫描对齐

每遍完整检查本次范围内的对象、已有上下文及直接关联的上下游；代码沿真实入口追到相关调用、数据和结果，不把“完整”扩大为每轮重读整个仓库。重点检查：

- 同一术语、字段、状态、职责的含义是否一致。
- 输入输出、触发条件、先后顺序、成功与失败的含义是否一致。
- 目标、约束、承诺、依赖与结果是否一致；例如方案承诺、实施任务和实际代码行为是否对应。
- 本次修改是否造成关联内容或依赖方未同步；例如关联段落、调用方、接口、测试或实施步骤。

发现有效冲突，按授权统一修订或修复，然后再完整扫描本次范围，不能只检查刚改的段落或函数。只审查或缺少决策时保留问题，继续不受影响的对抗检查，不能报告通过。修订后的最新版本完整扫描无冲突，再进入本轮对抗阶段。

### 3. 每轮调用 A、B 做对抗补漏

每次进入新一轮，都新建两个审查 Agent，提供同一份最新真实材料，让其完整独立检查；独立结果返回前不提供上一轮的通过结论、问题清单或辩论记录。随后提供上一轮完整状态供双方核对，合并同一问题的编号，再交换结果对抗，不能只核对旧问题。

先让 A、B 独立形成判断，再交换结果进行对抗：

1. A 推演被审对象如何满足目标，引用对应内容及证据；例如代码应引用真实调用链和数据变化，不能用设计意图代替实际实现。
2. B 提出具体反例，指出缺失的必要场景、隐藏前提、环节或有问题的行为；区分已证实问题和待验证假设。
3. A 逐条回应：引用已有处理方式和证据，或承认问题；不能用“实现时再处理”“已有测试”作为没有具体依据的覆盖证明。
4. B 检查回应，继续追问未闭环部分。主 Agent 转发必要反馈，直到问题成立、被证据排除，或明确缺少什么信息。

根据对象和目标挑选反例，例如前提不成立、边界条件、依赖失效、失败与部分成功、顺序变化等。并发、重试、权限或上线过渡等检查只在相关时使用，不机械套用无关场景。

角色长期指令以两个 TOML 定义为准；任务注明材料版本、文件位置、轮次、当前阶段和共同截止时间，按上述顺序补发完整状态、已有问题及对方结论。上面的停止规则也适用于本阶段内部往返。

如果当前环境不能调用多个 Agent，说明对抗阶段无法执行；单个 Agent 分饰两角不能标记为已完成多 Agent 对抗。

### 4. 验证反例，统一修订，再回到扫描

主 Agent 按依据和具体反例判断问题是否成立，不按票数或“双方同意”判定。每个问题说明成立条件、触发场景、缺失或出错位置、预期结果及实际或推演后果。验证方式随对象选择，例如核对规则、推演场景、复算结果或执行测试，区分推演与实际执行。

代码问题优先用最小复现或有意义的测试验证：记录实际执行命令及结果，必要时用可控并发顺序或故障点触发。能安全运行时由主 Agent 执行相关验证；无法运行时保留静态证据、推演路径和原因，不能冒称稳定复现或测试已通过。不运行会改写真实业务数据、发出消息或部署的操作来做验证，除非用户已授权相应操作。

在授权范围内统一修订被审对象及受影响的关联内容，更新问题清单，用同一反例复核。涉及代码修复时，运行与改动相关的测试、构建或类型检查；适用时补能防止同类问题再次发生的回归测试，不写只复述实现的测试。材料中的验收步骤只是待执行工作，不能据此声称实际验证通过。

修改后重新扫描本次完整范围及受影响上下游，交付本轮完整状态，注明修订后的版本“待下一轮独立复审”。预算允许且未触发停止规则时，下一轮回到步骤 2，重新扫描并新建 A/B。不能只让提出问题的一方局部验收，也不能在最后一轮对抗后继续改内容却沿用旧结论。未获修复授权时，不修改对象，报告未解决问题；即使首轮未修改且未发现问题，也要交付完整状态后进入独立验收轮。

## 结束条件

只有同时满足以下条件，才能报告审查通过：

1. 所有已确认、影响当前目标的必要冲突、遗漏与缺陷已解决并复核；可选优化不阻止通过。
2. 最后一次修改后，完整扫描本次范围、上下文及受影响上下游，没有发现有效冲突。
3. 已交付上一轮完整状态；随后新建无上一轮历史的 A/B，对同一最新版本先独立审查、再核对状态并完成对抗，没有新必要问题，也没有实质修订。
4. 与本次对象和结论相关的必要验证已完成，结果符合预期；验证失败或关键结论无法验证时，保留未完成项，不能无条件通过。不强制套用其他对象的验证手段，例如材料审查不要求不存在的代码测试。

如果最后一轮又修改了实质内容，上面的扫描和对抗结论就需要重新取得。扫描遍数和对抗轮数是记录，不是通过依据。

审查通过和停止审查是两个出口。触发预算或无进展上限、缺少关键依据或必要决策时，停止相应循环，交付未解决问题、未完成检查和下一步，标为“未通过”或“待确认”；停止不能代替通过条件。无进展只涉及单个争议时，预算内可完成其他独立检查，不重开该争议。

每轮及结束时均交付可独立读取的完整当前状态，记录扫描及对抗轮数和实际 Agent ID。区分未发现问题、已修复待独立复审、已复核、未修复及未验证，不承诺绝对零遗漏或零缺陷。
