# 业务应用程序建模

把现实世界中的工作、人、物和事件逐步映射为业务应用程序的职责与信息结构，再根据运行环境将其设计为软件整体结构、软件构件和数据库模式。始终区分业务模型与软件模型，并使后续设计能够追溯到需求。

## 建模原则

- 把业务应用视为现实世界的记录系统：数据结构应反映业务中的人、物、发生的事情及其关系。
- 用活动图理解实际工作情形，尤其是陌生的专业工作；不要一开始就假设系统功能。
- 把计算机的职责限定为擅长的“记忆工作”和“固定工作”。把需要情境判断、协商、伦理判断或专业裁量的工作保留给人，除非需求明确规定可执行规则。
- 把用例限定为对信息的输入或引用。输入包括登记、更新、取消和记录事件；引用包括检索、查询、核对、汇总和输出。
- 用类图表示系统应该记录的信息，而不是界面、按钮、服务、控制器或实现层对象。
- 把业务事件建模为类，例如借阅、预约、合同、交易；不要只把它们压缩成某个对象上的布尔值或状态字段。
- 显式标注多重性、角色名、标识信息和必要约束，使集合及其元素之间的关系可见。
- 区分面向对象的两种用途：用“归纳整理法”理解并组织现实世界，用“OOP 编程技术”组织软件构件、接口和实现。二者都用于设计，但产物不能直接等同。
- 防止“现实世界和软件结构是一样的”这一错觉。业务中的一个类不必对应一个代码类；一个业务概念可能由多个构件实现，一个构件也可能协调多个业务概念。
- 设计优先保证可维护性和可重用性，同时满足已明确的可靠性、效率、容量和时延目标；不要在没有测量与指标时以运行效率为由破坏结构。
- 不虚构关键业务规则。信息不足时列出“待确认问题”，并把为继续建模而采用的假设单独标明。

## 输出约定

优先使用目标文档能渲染的标准 UML。支持 PlantUML 时，用 PlantUML 绘制活动图、用例图和类图；仅支持 Mermaid 时，可以用带泳道标签的流程图近似活动图、用流程图近似用例图，并明确标注“用例图近似表示”，类图使用 `classDiagram`。图中的名称采用业务人员使用的语言。

每幅图之后列出它新增或验证了哪些模型元素。维护一张简短的追踪表：`现实活动 → 系统职责 → 用例 → 信息类/关系 → 子系统 → 软件构件/接口 → 数据表`。

## 工作流

### 0. 收集边界与词汇

确定业务目标、参与者、工作起点与终点、正常路径、例外路径、使用或产生的单据/信息，以及系统边界。为同义词选定统一业务术语。

### 1. 绘制现实业务活动图：定义需求

先只描述当前现实工作，不把待建系统画进去。使用泳道区分人员、组织或外部机构；表示动作、判断、并行、等待、返工和结束条件。

逐项标记活动：

- `记忆工作`：保存事实、历史、状态、期限和关联。
- `固定工作`：按稳定规则执行校验、计算、分类、通知或生成固定格式结果。
- `人的判断`：依赖专业裁量、沟通、谈判或例外处置。

据此给出“交给计算机的工作”清单。每项写明触发条件、所需信息、固定规则、记录结果及仍由人负责的判断。避免把当前手工步骤原样电子化；先说明其业务目的。

### 2. 绘制用例图：界定系统工作

把上一步的系统职责压缩成用例图。参与者放在系统边界外，用例放在边界内。

每个用例必须是信息的输入或引用，并以业务目标命名，例如“登记借阅”“查询可借图书”，不要使用“管理数据”“处理业务”等空泛名称。检查每个用例是否：

1. 有明确发起者；
2. 可追溯到步骤 1 的记忆工作或固定工作；
3. 说明输入、引用或二者兼有；
4. 没有混入人工专业判断。

仅在语义确切时使用 `include`、`extend` 和泛化，不为追求图形复杂度而添加关系。

### 3. 绘制纳入系统后的活动图

重新绘制未来工作情形，而不是复制步骤 1 的活动图。加入“业务系统”泳道，展示人员和系统如何协作完成业务。

把每个用例展开到实际流程中，标出信息输入、信息引用、自动校验/计算、持久化、反馈、错误与例外处理。清楚区分：

- 人作出业务判断，系统记录判断；
- 系统按固定规则作出确定性判定；
- 外部系统或机构完成的动作。

核对所有用例至少出现在一条流程中，并确认系统没有悄然接管步骤 1 中保留给人的判断。

### 4. 绘制信息类图

从前三步使用、产生和引用的信息中识别候选类，按以下顺序建模：

1. 人或组织：用户、顾客、职员、供应商等；
2. 物或业务对象：图书、商品、账户、单据等；
3. 发生的事情：借阅、预约、合同、交易、付款等；
4. 分类或规则对象：类别、费率、状态定义等，仅在业务上需要独立管理时建立。

为每个类列出业务标识、核心属性及必要状态。用关联、多重性和角色名表达关系；当关系自身具有日期、数量、状态、价格等信息时，把它提升为事件类或关联类。区分“一个实体可关联多个事件”的集合关系与“每个事件关联某个实体”的元素关系。

不要在此阶段加入数据库外键、表连接对象、API DTO 或技术类型。派生属性用 `/属性名` 标示；无法从事实推导的关键约束附在图旁。

### 5. 用文字解释类图

紧接类图，用业务语言描述：

- 系统记录哪些人、物和事件；
- 每个关系两端的含义与多重性；
- 一个典型业务事件如何把相关对象连接起来；
- 生命周期、唯一性、时间重叠或其他不能仅靠图完整表达的约束；
- 哪些内容不在系统记录范围内。

文字必须解释图，不要机械重复类名和属性。

### 6. 定义运行环境

在设计软件结构前，先记录运行约束并选择硬件、软件技术和产品。至少覆盖：

- 部署位置、硬件/计算资源、网络及外部设备；
- 操作系统、运行时、通信协议或中间件、数据库及关键平台产品；
- 可靠性、可用性、容量、响应时间、安全和恢复目标；
- 技术与产品成熟度、团队掌握程度、许可及总成本、供应商风险；
- 部署、监控、备份、升级、故障处理等运维便捷性。

先写约束和评价标准，再作选择。用决策表列出 `领域 / 候选方案 / 评价标准 / 选择 / 理由 / 风险`。区分已确定产品、建议方案和待验证假设；对重大选择给出验证或试验计划。

运行环境会改变后续设计方法。例如，关系型数据库会影响持久化边界，分布式通信会引入失败处理，嵌入式环境可能要求静态资源分配和线程规划。不要套用与环境无关的固定架构模板。

### 7. 定义软件整体结构

依据用例、质量属性、信息所有权和运行环境，把整体分割为职责明确的子系统。说明每个子系统：

- 负责哪些用例和业务规则；
- 拥有哪些信息，哪些信息只能经接口访问；
- 提供和依赖哪些接口；
- 部署到哪里，如何与外部系统通信；
- 发生故障时如何隔离、恢复或降级。

绘制子系统/构件图和依赖图。依赖箭头从依赖方指向被依赖方，并为重要依赖说明原因。嵌入式、实时或并发应用还要大致定义进程、线程、任务、中断及同步边界；普通业务应用只在并发模型影响正确性或质量属性时展开线程设计。

以可维护性和可重用性为主要结构目标：

1. 去除重复：把同一知识或规则集中到一个权威位置，不只消除外形相似的代码。
2. 提高构件独立性：让构件高内聚、接口小而稳定，隐藏内部决定，减少对其他构件实现细节的了解。
3. 避免循环依赖：构件依赖图必须是有向无环图。发现环时，通过重新分配职责、抽取共同抽象、引入事件或依赖倒置来消除；不要仅靠移动文件掩盖循环。

这些原则不是越多越好。抽取复用前确认概念及变化方向相同；为了消除依赖而引入的间接层必须有清楚职责。

### 8. 设计软件构件、类和接口

逐个确定实现各项功能的软件构件规格和接口。在 OOP 中进一步确定类与方法，但从职责和协作推导它们，不要把步骤 4 的信息类机械翻译为同名代码类。

对每个构件写明：

- 职责及不负责的内容；
- 提供接口、依赖接口、调用方向和生命周期；
- 输入、输出、前置条件、后置条件、不变量及错误语义；
- 状态所有权、事务边界、并发策略和资源释放责任；
- 对应的用例、业务规则、信息类和质量属性；
- 可替换性、测试接缝以及预期变化点。

需要类级设计时，分别标注以下角色：

- 领域类：表达业务状态、规则或事件；
- 应用类：编排用例和事务；
- 接口/适配器：连接 UI、数据库、消息或外部系统；
- 基础设施类：实现技术机制。

方法名表达业务意图；公开方法只暴露完成职责所需的最小契约。优先依赖稳定抽象，但不要为每个类无条件创建接口。通过构件图、软件类图或时序图验证协作，并再次检查重复、独立性与循环依赖。

### 9. 映射关系型数据库模式

类图经确认后，再给出关系模式草案：

- 每个持久化类通常映射为一张表；
- 对象标识映射为主键，关联映射为外键；
- 多对多关系映射为中间表；关系具有业务属性时，中间表应对应事件类；
- 值对象可按查询、约束和复用需要选择内嵌或独立成表；
- 补充唯一约束、非空约束、检查约束及必要索引；
- 不把可推导数据重复存储，除非明确说明性能或审计理由。

用表格列出 `表 / 主键 / 主要字段 / 外键 / 约束 / 来源信息类 / 负责构件`，并说明任何不直接对应信息类图的数据库设计决定。数据库模式是信息模型在特定运行环境中的持久化设计，不代表完整的软件构件设计。

### 10. 进行双模型复核

把“现实/业务模型”和“软件模型”并排复核：

| 复核对象 | 关注点 |
| --- | --- |
| 现实/业务模型 | 术语、人、物、事件、业务关系和规则是否真实、完整 |
| 软件模型 | 子系统、构件、接口、类、方法、线程和技术机制是否满足质量属性 |
| 两者映射 | 每个设计决定能否追溯到需求；差异是否有运行环境或质量属性方面的理由 |

明确记录有意的差异，例如：一个“借阅”业务事件由应用服务、领域对象、仓储和通知适配器共同实现。看到业务类名与代码类名一致时，不据此认定职责也相同；逐项检查状态、行为、生命周期和依赖方向。

## 完成检查

- 两张活动图表达的分别是“系统引入前的现实工作”和“系统引入后的协作工作”。
- 每个系统职责都来自记忆工作或固定工作，每个用例都能追溯到系统职责。
- 每个用例只表达信息输入或引用，并出现在系统活动图中。
- 类图覆盖用例所输入或引用的信息，也包含有业务意义的事件及多重性。
- 文字说明与信息类图一致，关系模式能逐项追溯到信息类图。
- 运行环境的选择有明确约束、评价依据、风险和验证方式。
- 软件整体结构覆盖所有用例和质量属性，子系统的信息所有权与接口清晰。
- 软件构件和类从职责、协作及运行约束推导，而不是信息类的一对一翻版。
- 重复知识有单一权威位置，构件保持独立，依赖图不存在循环。
- 现实/业务模型与软件模型分别表达，并记录二者之间的映射和有意差异。
- 假设、未决问题和系统边界清晰可见。
